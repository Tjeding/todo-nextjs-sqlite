# AI Usage

This document summarises how AI (Claude, via claude.ai) was used to build this project. It is a
summary of the actual working session, written from that session's history — the full raw
conversation should also be exported and attached alongside this file per the submission
requirements, since this document is a summary rather than a verbatim transcript.

## Starting point

The application began as a scaffold generated by ChatGPT: the full directory structure, a
`package.json`, an `.github/workflows/ci.yml`, and a couple of documentation files
(`docs/THIRD_PARTY_CODE.md`, `docs/RUNNING_IT.md`) — but every actual application file
(`app/`, `components/`, `lib/`, `database/schema.sql`, tests) was an empty stub. Claude was then
used to design and implement the entire application against that scaffold.

## Constraints stated up front

Before any code was generated, Claude was given the assignment brief directly (feature list,
fixed statuses, archive-not-delete, overdue-but-not-a-status, persistence-on-restart) and was told
explicitly to hold off on documentation, the AI-usage writeup, and expanding tests until the
application itself was working — i.e. scope was sequenced deliberately rather than generated in
one pass.

## Planning

Claude worked out the data model and page/route structure before writing code: one `tasks` table
(no user accounts, so no relational structure was needed), archiving represented as a nullable
`archived_at` timestamp on the same row (never a delete, never a copy to another table), and
overdue treated as a derived value computed at read time rather than a stored column — specifically
so it can never go stale relative to `due_date`/`status`, and so it can never accidentally become a
fourth selectable status.

## Code generation

Claude generated the schema, the data-access layer (`lib/taskRepository.ts`), validators, the
overdue rule, the API routes, the Next.js pages/components, and the test suite, then actually ran
the project (`npm install`, `npm run lint`, `npm test`, `npm run build`, and a live `npm start`
exercised with `curl` against every walkthrough step in the marking rubric — create, edit-and-
reload, archive, all three sort orders, the overdue badge, and a restart-persistence check by
reopening the SQLite file directly) rather than only generating code and assuming it worked.

## Debugging and a rejected output

The first implementation used `better-sqlite3` for the SQLite driver. When installed from a clean
`node_modules` in the sandbox, its native binding failed to build: no prebuilt binary was
available for the platform, and `node-gyp` could not fall back to compiling from source because it
needed to fetch Node headers from a domain the sandbox couldn't reach. Rather than paper over that
one-off environment issue, Claude treated it as a real risk for the actual grading environment too
(a clean clone with "nothing else to hand" is exactly the scenario where a native-binding install
failure would fail the entire walkthrough at step 1) and switched the whole data layer over to
Node's built-in `node:sqlite` module instead, which needs no native compilation at all. This
touched `lib/db.ts`, `lib/taskRepository.ts`'s type casts, `scripts/init-db.js`, and
`package.json`'s dependency list — and was re-verified with the full lint/test/build/walkthrough
pass again afterwards to confirm nothing regressed.

Smaller corrections during the same pass: an initial `eslint.config.mjs` flagged `require()` in the
two CommonJS scripts and an `any` cast in a test file; both were fixed (excluding the scripts from
the TypeScript-specific rule, and replacing `any` with the actual `Status` type) rather than
silencing the linter.
